# 千万次（TiMi）私链联调手册

> 目标：在没有真实资金的本地 EVM 私链上，把「充值 → 入账 → 参投 → 第N+3轮结算 → 提现出金 → 手续费销毁」整条链路跑通并逐项验证。
> 更新：2026-09-19（本轮实测全绿）。配套：[千万次-私链测试就绪清单.md](./千万次-私链测试就绪清单.md)

## 一、地址分工（这是最容易踩错的地方）

私链上有 **三个角色**，必须互不相同，否则监听会误判或漏单：

| 角色 | 谁 | 地址（hardhat 账户） | 配置项 |
|---|---|---|---|
| **充值收款地址** | 测试用户自己 | `0x7099…`（账户[1]） | `Chain.WatchPool` |
| **出金热钱包** | 只负责把 TM 转给用户 | `0x3C44…`（账户[2]） | `Withdraw.HotWalletPrivate` |
| **手续费池** | 持有手续费 TM 并执行 burn | `0xf39F…`（账户[0]） | `TronPool.Address` / `Burn.EvmPrivate` |

为什么必须分开：

1. `cmd/evmwatch` 的入账规则是「**to == WatchPool 且 from != WatchPool**」，并按 `to` 去 `wallet` 表查用户。
   - 所以 **WatchPool 必须是一个真实注册用户的地址**，不能是资金池——否则日志是「收款地址无对应用户，跳过」。
   - 若热钱包与 WatchPool 同址，每笔出金（池→用户）都会被当成充值重复入账（本轮实测复现过，已用 `from==pool` 过滤修掉）。
2. 出金热钱包必须持有 TM 与 gas；它的地址与充值地址不同，出金交易才不会污染充值监听。

⚠ 私链「充值」在测试里的等价做法：**直接给该用户的链上地址转账**（外部钱包充值在私链上没有外部可模拟），
然后让监听重扫认账。这条路径与真实充值走的是同一段代码。

```powershell

# 3) 建独立测试库（不要复用 crowd_local，那里有主网验证残留数据）
& "C:\Program Files\MySQL\MySQL Server 8.0\bin\mysql.exe" -uroot -p123456 `
  -e "CREATE DATABASE IF NOT EXISTS crowd_privchain DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"

# 4) 起服务（npower :3000）
cd ..\houduan\TiMi

.\build\ops.exe    -f config\etc.privchain.yml -port :5000   # 结算驱动用（-port 覆盖 yml 端口）
```

`config/etc.privchain.yml` 里必须与链一致的项：

| 配置 | 值 | 说明 |
|---|---|---|
| `Chain.FiboRpcUrl` | `http://127.0.0.1:8545` | 本地节点 |
| `Chain.FiboChainId` | `31337` | 写错 → 出金交易签名链 ID 不符被拒 |
| `Chain.TmContract` / `WatchToken` | 部署得到的地址 | |
| `Chain.Confirmations` | `1` | **必须调小**：hardhat 仅在有交易时出块，12 会让监听等 12 笔交易 |
| `Chain.WatchPool` | 测试用户地址 | 见 §一 |
| `Withdraw.Mode` | `broadcast` | 才真正出金上链 |
| `Withdraw.ChainAsset` | `TM` | 只有它允许链上出金，其余资产 fail-closed 拒绝 |
| `Burn.Chain` | `evm` | 走 ERC20 `burn(uint256)` 真实销毁 |

## 五、本轮踩到并修掉的坑（都是实测复现）

| # | 现象 | 根因 | 处置 |
|---|---|---|---|
| 1 | 提 USDT 却在链上转出 TM | `/api/withdraw` 无条件用 `Withdraw.TokenContract` 广播，资产与合约错配 | 新增 `Withdraw.ChainAsset` + `AssetContracts` 映射，解析不到就拒绝（fail-closed，扣账前预检） |
| 2 | 出金被当成充值重复入账 | 热钱包与充值池同址时，出金交易 `pool→用户` 命中监听过滤 | 入账前排除 `from == pool` / 自转 / mint，并用哨兵错误而非 `nil` 返回，避免被计成「已入账」 |
| 3 | 广播后交易 revert 却被当成出金成功 | 只判断 `SendTransaction` 不报错，不等回执 | `SendERC20` 增加回执轮询与状态判定；新增 `ErrTxReverted` / `ErrTxStatusUnknown`（超时保留哈希供人工核查，不重发） |
| 4 | 并发出金可能撞同一 nonce | `PendingNonceAt` 取 pending，热钱包并发出金时重复 | 热钱包出金串行化（按发送方地址加锁） |
| 5 | 前端提现的手续费永远不被销毁 | `/api/withdraw` 只扣费不写 `fee_burn`（而前端走的正是它） | 记账事务内补写 `fee_burn{status:0}` |
| 6 | 手续费币 TM 在 EVM 上没有销毁实现 | `cmd/burn` 只有 KTO 通道 | 新增 `Burn.Chain=evm` 分支，调 ERC20 `burn(uint256)`；带链上 decimals/totalSupply/余额三重预检与 7777 下限截断 |
| 7 | 监听扫不到新充值 | 进度键停在旧块，「无进度才用 -fromBlock」，hardhat 又不主动出块 | 脚本显式清进度键；`evmwatch` 增加 `last/safeHead` 与逐笔 Transfer 的 debug 日志 |
| 8 | 用校验和地址删不掉进度键 | Go 侧 `NormalizeAddress` 产出小写，Redis 键即小写 | 新增 `privchain-chain.mjs norm` 统一地址口径 |
| 9 | 参投报「当前阶段不支持该币种」 | TM 是手续费币种，阶段 1 只放行 FIBO/USDT | 私链脚本通过 `/ops/params` 切 `CurrentStage=2`（整体覆盖语义，必须先读再改再写） |
| 10 | 反复出现重复项目行 | 测试脚本清理不彻底，`project` 表累积多行同 (period,symbol) | `-Reset` 一并清 `project`；取项目按 `id DESC` |

## 六、私链不覆盖（需要真实链/其他服务）

- `utils/evm.SendERC20` 的**主网**行为（gasPrice 建议、EIP-155 链 ID、确认深度）——私链只验证了签名/广播/回执路径。
- KTO gRPC 通道与 TRON 通道：`cmd/burn`（KTO 分支）、`cmd/fundcollection`、`cmd/manualcollection`、`wallet/registration`、`ops/test/*`。
  **私链注册请统一走 `/api/auth/login`**（首登即注册，纯 EVM，不依赖 KTO/TRON）。
- 算力矿机产币的链上区块产出模型（`cmd/mining`）与经济数值仿真。
- 归集（collecting）没有 EVM 版本：私链上不做归集。

## 七、轮次推进的两条路径（别混用，否则测不到自动开轮）

| 路径 | 入口 | 做了什么 | 适用 |
|---|---|---|---|
| **A. 真实结算器** | `cmd/round` cron（每分钟 0 秒扫 `status=1 且 end_time<=now`） | `RoundManager.End`：抢占 status→2 → 退还超管本金 → 判成功/失败 → **第 N-MinRound 轮结算** → **AutoCreateNextRound 自动开下一轮** | 生产唯一路径；验证「自动开轮 + 最高限额递增」必须走它 |
| **B. 运维直调** | `POST /ops/endRound {roundId, act}` | 直接调 `RewardManager.Success/FailedNormal/Failed`，**完全绕过 `RoundManager.End`** | 只想快速结算/回滚某轮时用；不会自动开下一轮 |

⚠ **本轮踩到的坑**：一直用 B 路径做私链验证，于是「自动开轮」永远不触发，误以为需求 #2 没实现。
`scripts/privchain-e2e.ps1` 的第 `[6/7]` 步改为拉起真实 `round.exe` 跑一轮，并断言：
- 第 5 轮被自动创建，`target = 4000 × 1.3 = 5200`
- `max_vote` 由 10 → **11**（`RoundMaxVoteGrowRate=0.1`，需求 #2「最高限额每轮增加一点点」）
- `min_vote` 保持 1（需求 #2「最低限额不会更改」）

`RoundManager.End` 还有一个前置条件：结算第 (N-MinRound) 轮时，那一轮必须处于 `status=2（待结算）`；
若被 B 路径提前置成 3，`End` 会在 `First(&rewardRound)` 处报错并 return，**自动开轮也不会执行**。
私链脚本因此在拉起 `round.exe` 前把前 3 轮置回 status=2。

## 八、私链上「资金从哪来」速查

| 角色 | 谁付钱 | 私链做法 |
|---|---|---|
| 用户充值 | 手续费池（账户[0]）转 TM 给用户地址 | `privchain-chain.mjs send-token`，并在充值后再补 2 个空块（`Confirmations=1` 需要交易之后还有块才能扫到） |
| 用户参投 | 用户后台余额 | 先充值入账，再 `/api/participate`；金额要 ≤ 入账余额 |
| 出金给用户 | **出金热钱包（账户[2]）自己的 TM** | e2e 第 [3/7] 步会检查并在不足时从手续费池补 200 TM |
| 手续费销毁 | 手续费池（账户[0]）的 TM | `burn.exe` 调 `burn(uint256)` |
