## 二、🔴 私链阻塞项

### 阻塞1：没有私链节点，也没有对应的部署与配置产物

现状：
- `contracts/hardhat.config.js` 只有 `fibo`（主网）/`fiboTestnet`（`https://testnet.fibo.io`，chainId 仍写死 12306）/`hardhat`（内存网络，**进程退出即丢**）三个网络，**没有 `localhost` 持久节点的配置与用法**。
- `contracts/package.json` 的 `deploy:local` 指向 `--network hardhat`（跑到临时内存链上，产物无法被后端引用）。
- 后端 `config/etc.local.yml` 的 `Chain.FiboRpcUrl` 仍指向主网 `https://network.hzroc.art`，`TmContract` 为空。
- 没有「起链 → 部署 TM → 铸初始发行 → 生成后端配置 → 灌测试资金」的一键脚本。

要做：
1. `contracts/hardhat.config.js` 增加 `localhost`（`http://127.0.0.1:8545`，chainId 31337，type 0）网络；`package.json` 增加 `node:local` / `deploy:localnode` / `mint:localnode` 脚本。
2. 部署脚本产出 `contracts/deployments/localhost.json`（含地址、chainId、txHash）+ `deployments/abi/TMToken.json`（后端 EVM 销毁要按 ABI 编码 `burn(uint256)`）。
3. 新增 `houduan/TiMi/config/etc.privchain.yml`（私链专用，**不含任何主网私钥**）：RPC=127.0.0.1:8545、ChainId=31337、`TmContract`=部署地址、`Confirmations`=1、`Withdraw.Mode=broadcast`、热钱包与手续费池=hardhat 测试账户。
4. 一个可重入的本地准备脚本（`scripts/` 或 `houduan/TiMi/`）：起节点/部署/铸币/写配置/给测试用户发 TM 与 gas。

验收：`evmwatch -once -symbol TM -token <地址> -pool <池地址>` 能把私链上的一笔 TM 转账入账到 `wallet_point`，`wallet_hash_charge` 落 1 行。

### 阻塞2：手续费销毁只实现 KTO 通道，EVM 上没有销毁路径

现状：
- 需求（技术方案 1.7）：提币 3% 手续费以 **TM** 支付，**全部链上销毁**，直至 TM 仅剩 7777 枚。
- `cmd/burn/burn.go#L146` 唯一销毁调用是 `kto.KTOonChainSync(symbol, ...)`，即 **KTO gRPC 链**。
- 而 TM 是 EVM(ERC20) 代币（`contracts/contracts/TMToken.sol`，decimals=8，带 `burn(uint256)` 且合约层强制 7777 下限）。
- ⇒ 私链上「TM 手续费销毁」**完全无实现**，`fee_burn` 记录只会一直堆着。

要做：
1. `utils/evm/send.go` 增加 ERC20 方法调用能力：`EncodeERC20Burn(amount)`（selector=`keccak256("burn(uint256)")`）+ `SendERC20Call`（或让 `SendERC20` 支持任意 calldata），沿用现有 legacy 交易 + chainId 入参的写法。
2. `cmd/burn` 增加 EVM 分支：按 `impl.FeeSymbol` 是否为 EVM 代币选择通道（配置项驱动，例如 `Burn.Chain: kto|evm`），EVM 分支用 `Withdraw.TokenContract` / `Burn` 段配置的热钱包私钥调 `burn`。
3. 保留现有原子抢占语义（status 0/2 → 3 → 1 或回 2），**不要回滚**；链上成功但 DB 更新失败仍滞留 status=3 交人工。
4. 销毁前读 `remainingBurnable()` / `burnTargetReached()`，命中 7777 下限时停机并告警（与合约层双保险）。

验收：私链上 `fee_burn` 一笔待销毁 → `burn.exe` 执行 → 链上 `totalSupply` 减少、`FeeBurned` 事件可查、DB `status=1` 且记录 tx_hash；重复执行不重复销毁。

### 阻塞3：`/api/withdraw` 不写 `fee_burn`，而前端 DApp 走的正是这条

现状：
- `http/handler/wallet.go#L498-L504`（原生 `/wallet/withdraw`）在扣手续费后写 `fee_burn{status:0}`，交给 `cmd/burn` 销毁。
- `http/handler/apiadapter.go#Withdraw`（`/api/withdraw`，**前端 `WithdrawView.vue` 走这条**）只扣余额 + 写 `wallet_tx`，**完全没有 `fee_burn` 入队**。
- ⇒ 私链上用前端提现，手续费收了但永远不会被销毁，通缩模型在 EVM 侧断链。

要做：在 `/api/withdraw` 的记账事务里补写 `fee_burn`（与原生同口径，Symbol=`impl.FeeSymbol`、Amount=手续费最小单位、Status=0），失败则整事务回滚。

验收：`POST /api/withdraw` 后 `fee_burn` 新增 1 行 `status=0`，并可被 `cmd/burn` EVM 分支消费。

### 阻塞4：出金广播链路从未真实验证（含一个必然踩到的坑）

现状：
- `eevm.SendERC20`（`utils/evm/send.go`）只有「calldata 编码正确」与「非法入参在拨号前失败」两类单测；**主网阶段刻意没有广播过任何交易**（正确决策），所以私链是第一次真跑。
- `chainID` 由 `config.Chain.FiboChainId` 传入（默认 12306）。私链 chainId=31337 时**必须改配置**，否则签名链 ID 不符，节点直接拒收。
- 广播后**没有等待回执**：`broadcastWithdraw` 拿到 hash 就返回，`EstimateGas` 失败会静默回落 `100000`。
- `PendingNonceAt` 取的是 pending nonce：同一热钱包并发提现时，两笔可能拿到同一 nonce → 后者覆盖/被拒。

要做：
1. `SendERC20` 增加回执等待与状态判定（`bind.WaitMined` 的轻量替代：轮询 `TransactionReceipt` 直到 status=1 或超时），失败必须返回错误。
2. 广播前做链上 `decimals`/`symbol` 校验（防止把 TM 合约地址配错成别的代币）。
3. 同一热钱包出金串行化（Redis 锁 `npower:withdraw:hotwallet`，或非严格场景下用「先取 nonce 再发」的排队）。
4. 私链验证脚本：提现 → 查链上 `Transfer` 事件 → 校验收款方与金额 → 校验 DB `wallet_tx.hash` 已从 `local-*` 更新为真实 hash。

验收：私链上 `POST /api/withdraw`（Mode=broadcast）→ 收款地址链上余额增加、`wallet_tx.hash` 为 0x 开头真实交易哈希、receipt status=1。

## 三、🟡 私链适配项

### 适配5：`Confirmations=12` + 私链出块方式 = 监听卡死

- `evmwatch` 用 `safeHead = head - Confirmations`；hardhat node 默认**只在有交易时出块**。若确认数写 12，则必须再发 12 笔交易，那笔充值才可见。
- 处理：私链配置 `Chain.Confirmations: 1`；并在准备脚本里用 `hardhat_setIntervalMining`（或定期 no-op 交易）保证出块，避免监听停摆。

### 适配6：原生注册接口依赖 KTO gRPC（私链不可用）

- `core/impl/wallet.go#Registration` → `kto.CreateWallet()`（gRPC 调 KTO 节点）与 `tron.CreateAccount()`；`ops.go#TestAccounts`、`ops.go#SupperWallet` 同样依赖。
- `/api/auth/login` 首登注册（`handler/auth.go#authRegister`）**不依赖 KTO**，纯 EVM 地址入库 —— 这是私链应当走的主路径。
- 处理：私链测试统一走 `/api/auth/*`；原生 `/wallet/registration` 与 `ops/test/*` 明确标注「私链不适用」，或后续增加「生成随机 EVM 地址」的本地钱包分支。

### 适配7：测试库残留主网验证数据

- `crowd_local` 里有 2026-09-18 主网只读验证留下的测试钱包 `EVMTEST01`(id=17) 与 2 条真实充值记录（`wallet_hash_charge`），另有历史重复轮号（`project=1 round=2` 两行，recon 会报 ERROR）。
- 处理：私链测试前先决断——清理这些行，或另建 `crowd_privchain` 库从零 AutoMigrate（推荐后者，验证「新建库唯一约束不丢」这条历史坑）。

### 适配8：归集与挖矿的链上环节没有 EVM 版本

- `cmd/fundcollection`（`collecting.go`/`u_collect.go`）与 `cmd/manualcollection` 只用 TRON/KTO；`cmd/burn` 见阻塞2；`cmd/mining` 的产出模型依赖链上区块产出。
- 处理：私链测试范围先限定为「充值/参投/结算/提现出金/手续费销毁」，归集与挖矿标注为不覆盖。

### 本轮实测暴露并修掉的两个资金级缺陷

1. **资产/合约错配**：`/api/withdraw` 无条件用 `Withdraw.TokenContract` 广播，提 USDT 会在链上转出 TM。
   → 新增 `Withdraw.ChainAsset`（+可选 `AssetContracts`/`AssetDecimals` 多资产映射），解析不到即拒绝，且在扣账前预检。
2. **出金被当成充值重复入账**：出金热钱包与充值监听池同址时，出金交易 `pool→用户` 命中监听过滤条件。
   → 入账前排除 `from == pool` / 自转 / mint；并把「跳过」从返回 `nil` 改为哨兵错误（返回 `nil` 会被计成已入账，日志与真实结果不符）。
